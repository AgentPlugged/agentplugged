# Choosing a method

The creator may name one, or two to blend. Otherwise choose by what the document is and what it
risks, and say why in one line. Identifiers are those of the report; the file is
`references/<identifier with - for _>.md`.

- **brief**: `socratic` (premises nobody questioned); `reframe` if it may answer the wrong question.
- **prd**: `pre_mortem` (what it forgot); `subtraction` if long; `extreme_user` if users are varied.
- **ux**: `devils_advocate` (defended by whoever drew it); `extreme_user`; `subtraction` for excess.
- **architecture**: `divergence` (two parts true to each decision that still do not fit);
  `red_team` (adversary and load); `failure_modes` (each part failing); `compare_existing` when
  code already exists.
- One big assumption: `first_principles`, or `assumption_audit` for several.
- A hard-to-reverse decision: `inversion`, `second_order` (what it causes next), `steelman` (the
  best case for the option dropped).
- Whether a PRD or a UX specification is good as a whole (thesis, theater, trade-offs, excess):
  `judgment`, whose grid is in the checklist of the skill that wrote it.
- A regulated or specialised field: `domain_expert`.

**Blend**: two methods in one critique when the risks differ (`divergence` with `failure_modes`);
`lenses` holds both, the sub-agent reads both files, the report stays one and holds the 12
strongest objections. Never three. `personas` and `reconcile` stand alone.

**Reconcile** (`reconcile`): before a PRD, UX or architecture is validated, not instead of a
critique; at most five findings, see `references/reconcile.md`.

A third method, or another with a different aim, is a new critique.
