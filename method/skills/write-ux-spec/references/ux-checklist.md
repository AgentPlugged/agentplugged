# UX specification checklist

Run every check before showing the specification to the creator. Fix what fails; when a fix
needs the creator, ask them, one question at a time, or open a `decision` checkpoint.

## Header and identifiers

- The header is the first thing in the file and holds `id: ux`, `kind: ux`, `owner: stella` and
  `links`: `prd` and every `PU-n` and `EF-n` the specification covers, all active in the PRD.
- No `status`, `state`, `cost`, `spent`, `budget_spent` or `progress` key.
- No requirement identifier is defined: none opens a line, a list item, a heading or a first
  table cell.
- No `<…>` placeholder is left from the template, no value marked `(sample)` (the sample
  colours `#FFFFFF`, `#111111`, `#1A1A1A`, `#F2F2F2`, `#0F62FE`, `#78A9FF`, sizes `16px`, `24px`, `400`, `600`, `1.5`, `1.25`, spacings
  `4px`, `8px`, radius `8px`) unless the creator chose that exact value, no sample link (`PU-1`,
  `EF-1`) the specification does not cover, and no `screen-sample.html`.
- No `[open: G-…]` mark remains for a decision the creator already answered, and none sits at
  the start of a line or before an identifier.
- `npx agentplugged docs check` reports no problem.

## Coverage

- Every journey of the PRD has a key flow, with its moment of value and its failure path.
- Every screen serves at least one journey, and every journey lands on screens.
- Every flow names the requirements it covers; the "Traceability" table agrees with the flows.
- Every screen lists the states that apply (empty, loading, error, success, offline, permission
  denied), with what the user sees.
- Nothing in the specification asks for a capability the PRD does not state: such a need is an
  open question.

## Visual identity

- Every colour token has a hexadecimal value for each mode the product supports.
- Every token used in the text (`{…}`) is defined once, in the `tokens` block of the header
  (`docs check` refuses one that is not); on a UI system the product keeps, `ui_system` is
  declared and the tokens hold only the difference.
- Every component used in a flow has a visual specification and a behaviour.
- The visual direction is the one the creator chose; every guess is marked `[assumption]`.

## Screens, sketches and pages

- Every screen of the architecture has a sketch whose regions are numbered the same in the
  drawing and in the list; the key screens (two to four) each have a page, or `none` by the
  creator's choice.
- Each page was drawn from the tokens and the sketch, shows the product's own words, and
  `ux.md` states once that the specification wins over any page.
- Every component, state and accessibility fix a story must carry is a `UX-n` of "Elements to
  build", none renumbered.

## Accessibility

- Every item of `references/accessibility-check.md` has a result in "Accessibility check".
- No blocking finding is left without a fix or the creator's explicit acceptance.

## Excess (over-specification)

A specification says each thing once, at the level a builder needs. Each excess is a finding,
minor unless it hides a decision; for an independent verdict, ask a sub-agent for the method
`judgment` (skill `critique-deliverable`), reported in its closed form.

- **One home per value.** A size, colour or duration written inline that a token already names,
  or that a rule would give.
- **One home per fact.** Content copied from the PRD that its identifier would carry.
- **A reader per section.** Ask who would miss it; a section nobody builds from, or a story
  about the brand that settles no choice, goes.
- **Reachable.** A screen or a state that no journey of the PRD reaches.

## Form

- The terms are those of the PRD's glossary.
- Tables are used where they read better than prose; no section is padded.
- No guidance comment and no "Generated by agentplugged" line is left.
- The stack and the code are left to Alex and the developers: a preference is noted, never
  decided.
